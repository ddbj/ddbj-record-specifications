# ST.26 対応に関する調査・設計メモ

## 背景

PR #1 (<https://github.com/ddbj/ddbj-record-specifications/pull/1>) で、WIPO ST.26（特許配列リスト）形式のデータを扱うためのスキーマ拡張が提案されている。
本メモは、ST.26 規格の調査結果、PR で追加された各フィールドの評価、およびスキーマ設計の方向性をまとめたものである。

## WIPO ST.26 規格の概要

WIPO Standard ST.26 は、特許出願における塩基配列・アミノ酸配列リストを XML 形式で記述するための国際標準である。
旧規格 ST.25（プレーンテキスト）を置き換え、2022 年 7 月 1 日以降の特許出願で必須となった。

### ST.26 XML の全体構造

```
ST26SequenceListing (root)
├── ApplicationIdentification?     # 出願識別（出願済みの場合）
│   ├── IPOfficeCode               # 知財庁コード（WIPO ST.3）
│   ├── ApplicationNumberText      # 出願番号
│   └── FilingDate?                # 出願日
├── ApplicantFileReference?        # 出願人ファイル参照番号（未出願の場合）
├── EarliestPriorityApplicationIdentification?  # 最先優先権出願
│   ├── IPOfficeCode
│   ├── ApplicationNumberText
│   └── FilingDate?
├── ApplicantName?                 # 出願人名（languageCode 属性必須）
├── ApplicantNameLatin?            # 出願人名（ラテン文字翻字）
├── InventorName?                  # 発明者名（languageCode 属性必須）
├── InventorNameLatin?             # 発明者名（ラテン文字翻字）
├── InventionTitle+                # 発明の名称（言語ごとに複数可、languageCode 属性必須）
├── SequenceTotalQuantity          # 配列総数
└── SequenceData+                  # 配列データ（INSDC サブセット）
    └── INSDSeq
        ├── INSDSeq_length
        ├── INSDSeq_moltype        # DNA / RNA / AA
        ├── INSDSeq_division       # "PAT" 固定
        ├── INSDSeq_other-seqids?  # pat|{office}|{pub_number}|{kind}|{seq_id}
        ├── INSDSeq_feature-table?
        │   └── INSDFeature+       # source feature + annotation features
        └── INSDSeq_sequence
```

### ST.26 と INSDC/DDBJ の関係

- ST.26 の配列データ部分は INSDC DTD のサブセットとして設計されている（`INSDSeq`, `INSDFeature`, `INSDQualifier` など）
- 特許庁（JPO, KIPO → DDBJ、USPTO → GenBank、EPO → ENA）から INSDC データベースへ配列データが提供される
- `INSDSeq_division` は `"PAT"` 固定（GenBank/DDBJ の PAT division に対応）
- INSDC 間で日次データ同期が行われ、全特許配列が世界中で利用可能になる

### 参考資料

- WIPO ST.26 DTD V1.3: <https://www.wipo.int/standards/dtd/ST26SequenceListing_V1_3.dtd>
- USPTO MPEP Section 2413: <https://www.uspto.gov/web/offices/pac/mpep/s2413.html>
- DDBJ 特許データ: <https://www.ddbj.nig.ac.jp/ddbj/patent-data-e.html>
- ST.26 Annex III specimen XML: <https://www.wipo.int/standards/en/xml_material/st26/st26-annex-iii-sequence-listing-specimen.xml>

## PR #1 で追加された各フィールドの評価

### 1. `Provenance.source_format` への `"ST26"` 追加

- v2: `Literal["GFF", "TradAnnotation"]`
- draft: `Literal["GFF", "ST26", "TradAnnotation"]`
- **評価**: 妥当

### 2. `Source.tax_id` (`int | None`)

| 項目 | 内容 |
|------|------|
| ST.26 対応要素 | **なし**（ST.26 DTD に taxonomy ID 要素は存在しない） |
| INSDC での扱い | `/db_xref="taxon:XXXX"` として source feature に記録される |
| DDBJ での扱い | **データベース側が自動付与**。提出者が直接指定するものではない |

ST.26 XML には organism 名（テキスト）しか含まれず、数値の TaxId は存在しない。
INSDC フラットファイルでは `/db_xref="taxon:9606"` のように自動付与される。
このフィールドは ST.26 由来というより、DDBJ への取り込み時に名前解決した結果を保持するための補助フィールドと考えられる。

### 3. `ApplicationIdentification` モデル（新規クラス）

ST.26 DTD: `<!ELEMENT ApplicationIdentification (IPOfficeCode, ApplicationNumberText, FilingDate?)>`

| PR のフィールド | ST.26 要素 | 必須/任意 | 説明 |
|----------------|-----------|----------|------|
| `ip_office_code: str` | `IPOfficeCode` | 必須 | 知財庁コード（例: `JP`, `US`, `EP`） |
| `application_number_text: str` | `ApplicationNumberText` | 必須 | 出願番号 |
| `filing_date: str \| None` | `FilingDate` | 任意 | 出願日（ISO 8601） |

**評価**: ST.26 DTD と概ね一致。フィールド名の snake_case 変換も妥当。

### 4. `Submission.invention_title` (`str | None`)

| 項目 | 内容 |
|------|------|
| ST.26 要素 | `InventionTitle` |
| ST.26 での扱い | **必須**（出願言語で1つ、翻訳で追加可能、`languageCode` 属性必須） |

**懸念点**:

- ST.26 では複数の `InventionTitle` を持てる（言語ごと）が、PR では単一 `str`
- `languageCode` 属性の情報が欠落

### 5. `Submission.publication_date` (`str | None`)

| 項目 | 内容 |
|------|------|
| ST.26 要素 | **存在しない** |
| ST.26 にある日付要素 | `FilingDate`（出願日）、`productionDate`（XML 生成日、ルート要素属性） |

**懸念点**: `PublicationDate` は ST.26 DTD に定義されていない。特許の公開日は特許庁の公開プロセスで決まるもので、配列リスト XML 自体には含まれない。ST.26 XML 外の特許書誌メタデータ（WIPO ST.36/ST.96 など）から補完する情報と考えられる。出典を明確にすべき。

### 6. `Submission.applicant_name` (`str | None`)

| 項目 | 内容 |
|------|------|
| ST.26 要素 | `ApplicantName` + `ApplicantNameLatin` |
| ST.26 での扱い | 最初の（主要な）出願人の名前のみ。`languageCode` 属性必須 |

**懸念点**:

- `languageCode` 属性の情報が欠落
- 非ラテン文字の場合に必須の `ApplicantNameLatin`（翻字）フィールドがない

### 7. `Submission.inventor_name` (`str | None`)

| 項目 | 内容 |
|------|------|
| ST.26 要素 | `InventorName` + `InventorNameLatin` |
| ST.26 での扱い | 任意。最初の発明者の名前のみ。`languageCode` 属性必須 |

**懸念点**: `applicant_name` と同様。`languageCode` と Latin 翻字フィールドが欠落。

### 8. `Submission.application_identification` (`ApplicationIdentification | None`)

| 項目 | 内容 |
|------|------|
| ST.26 要素 | `ApplicationIdentification` |
| ST.26 での扱い | 出願済みなら必須（`ApplicantFileReference` と排他的に使用） |

**懸念点**: ST.26 では `ApplicationIdentification` がない場合に `ApplicantFileReference` が必須になるが、PR にはこのフィールドがない。

### 9. `Submission.earliest_priority_application_identifications` (`list[ApplicationIdentification] | None`)

| 項目 | 内容 |
|------|------|
| ST.26 要素 | `EarliestPriorityApplicationIdentification` |
| ST.26 での扱い | 任意（優先権主張がある場合に使用） |
| ST.26 での多重度 | **単数**（`?` = 0 個または 1 個） |

**懸念点**: ST.26 DTD では単数だが、PR では `list`（複数）。意図的な拡張か確認が必要。

### 指摘まとめ

| # | 指摘 | 重要度 |
|---|------|--------|
| 1 | `publication_date` は ST.26 DTD に存在しない要素。出典を明確にすべき | 高 |
| 2 | `earliest_priority_application_identifications` が `list` だが ST.26 では単数 | 中 |
| 3 | `invention_title`, `applicant_name`, `inventor_name` に `languageCode` がない | 中 |
| 4 | `ApplicantNameLatin`, `InventorNameLatin`（非ラテン文字時の翻字）がない | 中 |
| 5 | `ApplicantFileReference`（出願番号がない場合の代替 ID）がない | 低 |
| 6 | `tax_id` は ST.26 由来ではなく INSDC/DDBJ 側の補助情報。説明があると良い | 低 |

## スキーマ設計の方向性

### 現状の問題

v2 の `Submission` は 11 フィールド（うち 5 が Optional で形式固有）。
PR #1 で ST.26 固有の 6 フィールドが追加されると、合計 17 フィールド（うち 11 が Optional で形式固有）になる。
今後 format が増えるたびに Optional が増殖する構造。

```
v2 Submission (11 fields)
├── 共通 (4): submitters, db_xrefs, references, comments
├── ほぼ共通 (2): hold_date, division
└── 形式固有 (5, all Optional):
    ├── TradAnnotation: trad_submission_category, locus_tag_prefix
    └── WGS: seq_prefix, keywords, datatype

draft Submission (17 fields)
├── 共通 (4)
├── ほぼ共通 (2)
└── 形式固有 (11, all Optional):     ← 増殖
    ├── TradAnnotation: trad_submission_category, locus_tag_prefix
    ├── WGS: seq_prefix, keywords, datatype
    └── ST.26: invention_title, publication_date, applicant_name,
              inventor_name, application_identification,
              earliest_priority_application_identifications
```

### 選択肢 A: v2.x のまま Optional を追加（現 PR の方針）

```python
class Submission(BaseModel):
    # 共通
    submitters: list[Person]
    db_xrefs: list[Xref]
    references: list[Reference]
    comments: list[list[str]]
    hold_date: str | None
    division: str | None
    # TradAnnotation 固有
    trad_submission_category: Literal["WGS", "GNM"] | None
    locus_tag_prefix: str | None
    seq_prefix: str | None
    keywords: list[str] | None
    datatype: str | None
    # ST.26 固有
    invention_title: str | None
    applicant_name: str | None
    ...
```

- メリット: 後方互換、既存コードの変更不要、シンプル
- デメリット: フィールドが増えるほど「何が何用か」不明瞭。型レベルで誤用を防げない

### 選択肢 B: v3 で Discriminated Union（タグ付きユニオン）

`source_format` で分岐する形式固有の Submission モデルを作る。

```python
class CommonSubmission(BaseModel):
    """全形式で共通のフィールド"""
    submitters: list[Person]
    db_xrefs: list[Xref]
    references: list[Reference]
    comments: list[list[str]]
    hold_date: str | None
    division: str | None

class TradSubmission(CommonSubmission):
    source_format: Literal["TradAnnotation"]
    trad_submission_category: Literal["WGS", "GNM"]
    locus_tag_prefix: str | None
    seq_prefix: str | None
    keywords: list[str] | None
    datatype: str | None

class ST26Submission(CommonSubmission):
    source_format: Literal["ST26"]
    invention_title: str  # ST.26 では必須
    applicant_name: str | None
    inventor_name: str | None
    application_identification: ApplicationIdentification | None
    earliest_priority_application_identification: ApplicationIdentification | None
    ...

class GFFSubmission(CommonSubmission):
    source_format: Literal["GFF"]

Submission = Annotated[
    TradSubmission | ST26Submission | GFFSubmission,
    Discriminator("source_format"),
]
```

- メリット: 型レベルで「この形式にはこのフィールドが必要/不要」が明確。形式ごとに必須/任意を正しく表現できる
- デメリット: 破壊的変更（v3 + converter 必要）。新形式追加のたびにクラスが増える。JSON Schema が union になり複雑になる

### 選択肢 C: v3 で共通部分 + 拡張辞書（柔軟性重視）

共通フィールドだけ型付けし、形式固有は構造化した拡張領域に置く。

```python
class Submission(BaseModel):
    # 共通フィールド（型安全）
    submitters: list[Person]
    db_xrefs: list[Xref]
    references: list[Reference]
    comments: list[list[str]]
    hold_date: str | None
    division: str | None
    # 形式固有の拡張
    extensions: dict[str, Any] | None  # or a typed union
```

- メリット: Submission のコアが安定する。新形式追加で Submission 自体は変わらない
- デメリット: extensions 内の型安全性が弱い。バリデーションが複雑になる

### 選択肢 B の追加考察: Submission 以外のモデルへの波及

案 B を採用した場合、Submission だけでなく他のモデルでも同様の問題が発生しうる。

#### 各モデルの形式依存性

| モデル | TradAnnotation | GFF | ST.26 | 形式間の差 |
|--------|---------------|-----|-------|-----------|
| **Submission** | WGS/GNM 固有 5 fields | ほぼ共通のみ | 特許固有 6 fields | **大きい** |
| **Source** | organism, mol_type, qualifiers | 同左 | + `tax_id`（補助） | 小さい（今は） |
| **Entry** | type, topology 等 | 同左 | division="PAT" 固定、`INSDSeq_other-seqids` 形式固有 | 今後増えうる |
| **Feature** | INSDC feature table | GFF3 由来 | INSDC subset（ST.26 制約あり） | qualifier の制約が異なる |
| **Experiment** | ST_COMMENT 由来 | 使わない？ | 使わない | 有無が形式依存 |
| **Provenance** | `extra="allow"` で吸収 | 同左 | 同左 | 問題なし |

現時点では Submission が最も顕著だが、今後を考えると:

- Entry に特許固有メタデータ（`INSDSeq_other-seqids` のパース結果など）が入る可能性がある
- Feature/Source の qualifier バリデーションルールが形式で異なる（ST.26 は INSDC のサブセットで制約が厳しい）
- 新形式が増えるたびに、どのモデルにも Optional が生える可能性がある

#### 選択肢 B': 全モデルに Discriminated Union を適用

```
DdbjRecord
├── submission: TradSubmission | ST26Submission | GFFSubmission
├── sequences: TradSequences | ST26Sequences | GFFSequences
├── features: ...
└── ...
```

全モデルに union を適用すると型安全だが、**組み合わせ爆発**する。
`TradSubmission` + `ST26Sequences` のような不整合な組み合わせも型上は許されてしまう。
クラス数も `モデル数 × 形式数` に膨れる。

### 選択肢 D: DdbjRecord レベルで Extension 分離

形式固有の情報を各モデルに散らさず、ルートレベルで 1 箇所にまとめる。

```python
# コアモデル（形式非依存、安定）
class Submission(BaseModel):
    submitters: list[Person]
    db_xrefs: list[Xref]
    references: list[Reference]
    comments: list[list[str]]
    hold_date: str | None
    division: str | None

class Sequences(BaseModel):
    common_source: Source
    entries: list[Entry]

# 形式固有モデル（それぞれ独立）
class TradAnnotationExtension(BaseModel):
    trad_submission_category: Literal["WGS", "GNM"]
    locus_tag_prefix: str | None
    seq_prefix: str | None
    keywords: list[str] | None
    datatype: str | None

class ST26Extension(BaseModel):
    invention_title: str
    applicant_name: str | None
    inventor_name: str | None
    application_identification: ApplicationIdentification | None
    publication_date: str | None
    ...

# ルートで統合
class DdbjRecord(BaseModel):
    schema_version: str
    provenance: Provenance
    submission: Submission          # 共通フィールドのみ
    experiments: list[Experiment]
    sequences: Sequences
    features: list[Feature]
    # 形式固有は 1 箇所に集約
    trad_annotation: TradAnnotationExtension | None
    st26: ST26Extension | None
    # 将来: jga: JGAExtension | None
```

- メリット:
  - コアモデル（Submission, Source, Entry, Feature）が形式非依存で安定する。新形式追加でこれらは変わらない
  - 形式固有フィールドが 1 箇所に集約されるので、「何が ST.26 用か」が一目瞭然
  - 各 Extension 内で形式ごとの必須/任意を正しく表現できる（`invention_title` を必須にする等）
  - Discriminated Union の組み合わせ爆発が起きない
  - JSON Schema も `oneOf` ではなく単純な Optional object で表現できるので利用者に分かりやすい
- デメリット:
  - `trad_annotation` と `st26` が同時に非 `None` な状態を型だけでは防げない（バリデーションで対応）
  - `provenance.source_format` との一貫性チェックが必要
  - 既存の `trad_submission_category` 等を Submission から Extension に移す破壊的変更が発生する

#### 案 D の JSON 利用面での懸念

利用者が JSON を扱う際、意味的に近い情報が離れた場所に分散する。

```jsonc
// 案 D: 情報が分散
{
  "submission": { "submitters": [...] },
  "st26": { "applicant_name": "..." }
}

// 案 A: 同じ場所にある
{
  "submission": {
    "submitters": [...],
    "applicant_name": "..."
  }
}
```

「submitter の情報と applicant_name を一緒に表示したい」のような処理で 2 箇所を参照する必要がある。
jq やスクリプトでの取り回しが煩雑になる。

### 選択肢 E: フラット + バリデーションルールで制約（推奨案）

JSON の構造はフラット（案 A 寄り）のまま、形式ごとの「どのフィールドが必須/禁止か」はバリデーション層で担保する。

```python
# スキーマ定義はフラット（利用者が触る JSON はシンプル）
class Submission(BaseModel):
    # 共通
    submitters: list[Person]
    db_xrefs: list[Xref]
    references: list[Reference]
    comments: list[list[str]]
    hold_date: str | None
    division: str | None
    # TradAnnotation 用
    trad_submission_category: Literal["WGS", "GNM"] | None
    locus_tag_prefix: str | None
    seq_prefix: str | None
    keywords: list[str] | None
    datatype: str | None
    # ST.26 用
    invention_title: str | None
    applicant_name: str | None
    inventor_name: str | None
    application_identification: ApplicationIdentification | None
    earliest_priority_application_identifications: list[ApplicationIdentification] | None
    ...
```

バリデーション層（既存の Stage 3 拡張 or 新 Stage）で形式固有ルールを追加する:

```python
# バリデーションルールの例（概念）
FORMAT_RULES = {
    "ST26": {
        "required": ["invention_title"],
        "optional": ["applicant_name", "inventor_name", ...],
        "forbidden": ["trad_submission_category", "seq_prefix", "keywords", "datatype"],
    },
    "TradAnnotation": {
        "required": ["trad_submission_category"],
        "optional": ["locus_tag_prefix", "seq_prefix", ...],
        "forbidden": ["invention_title", "applicant_name", ...],
    },
}
```

- メリット:
  - JSON がフラットで使いやすい（利用者に優しい）
  - 「ST.26 なのに `seq_prefix` が入ってる」のような誤用をバリデーションで検出できる
  - Pydantic の型だけでは表現しきれない形式横断の制約（「`seq_prefix` は `trad_submission_category="WGS"` の時だけ有効」等）も自然に書ける
  - 既存の 4 段階バリデーションの延長線上にある
  - 破壊的変更を最小化できる（v2.x で追加可能、v3 にする必要がない）
  - Submission 以外のモデル（Source, Entry 等）にも同じパターンを適用できる
- デメリット:
  - 型レベルでは制約が見えない（JSON Schema だけ見ても「ST.26 で何が必須か」分からない）
  - ドキュメントで補う必要がある
  - Optional 増殖の「見た目の問題」は残る（コメントやグルーピングで緩和）

### 全選択肢の比較

| | Submission の設計 | 他モデルへの波及 | JSON の使いやすさ | 型安全性 | 破壊的変更 | 拡張性 |
|---|---|---|---|---|---|---|
| A (フラット Optional) | Optional 増殖 | 同じ問題が再発 | **良い** | 低 | なし | 低 |
| B (Submission だけ Union) | 解決 | 未解決 | 普通 | 中 | v3 必要 | 中 |
| B' (全モデルに Union) | 解決 | 解決 | 普通 | 高 | v3 必要 | 低（組み合わせ爆発） |
| C (拡張辞書) | 解決 | 解決 | 普通 | 低 | v3 必要 | 高 |
| D (ルート Extension) | 解決 | 解決 | **悪い**（情報分散） | 中 | v3 必要 | 高 |
| **E (フラット + バリデーション)** | 緩和 | 同パターンで対応可 | **良い** | 低（バリデーションで補完） | なし (v2.x) | 高 |

### 検討ポイント
