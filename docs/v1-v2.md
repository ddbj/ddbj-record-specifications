# v1 / v2

v1 と v2 は、DFAST が出す Trad (塩基配列) の登録データを表す古い major である。
DFAST と dr_tools が使っているので残しているが、新しく使うものは v3 を使う。v1 / v2 には新しい登録形式への対応を足さず、直すのは不具合だけにする。

## v1 と v2 の違い

| major | 形 | 主なキー |
|---|---|---|
| v1 | DFAST (dfast_core) の出力に合わせた平らな形 | `COMMON`、`COMMON_SOURCE`、`COMMON_META`、`ENTRIES` |
| v2 | 登録者・実験・配列・feature を分けた形 | `provenance`、`submission`、`experiments`、`sequences`、`features` |

- v1 の `trad_submission_category` は `"WGS"` か `"GNM"` だけなので、ウイルス (DFAST_VRL) のデータは v2 でしか表せない
- v2 の `submission.submitters` は、先頭の人が連絡先である

v2 には次の設計上の問題があり、v3 はこれを分け直している ([v3-schema.md](./v3-schema.md))。

- `Submission` に、登録の手続き、データの分類、配列の名前の付け方が混ざっている
- Trad の ST_COMMENT を `Experiment` に置いている

## schema_version

v1 / v2 の record は minor 付きの `schema_version` を持つ。型は古い書き方も読み、その major の最新の minor にそろえる。

| 読む値 | そろえた値 |
|---|---|
| `"0.1"`、`"v1"`、`"v1.0"` | `"v1.0"` |
| `"0.2"`、`"v2"`、`"v2.0"` - `"v2.3"` | `"v2.3"` |

## v1 と v2 の間の変換

`ddbj_record/converter/` の v1 -> v2 と v2 -> v1 で変換する。

- v1 -> v2 では情報を失わない。v1 -> v2 -> v1 で元に戻る。ただし、次の 2 つは変わることがある
  - 連絡先の人が先頭に来るので、`ab_name` の順序
  - entry の source feature に `COMMON_SOURCE` と同じ organism / mol_type を重ねて書いていたとき、戻った source feature からはその 2 つが消える。v1 の entry の source feature は entry 固有の情報だけを持つので、v2 -> v1 では `COMMON_SOURCE` と同じ値を書かない。逆に v2 の `Source` は organism と mol_type が必須なので、v1 -> v2 では無いものを `COMMON_SOURCE` から写す
- v2 -> v1 では、v1 に置き場所の無い情報を失う。失うときは `UserWarning` を出し、変換は止めない。v2 -> v1 -> v2 で元に戻ることは保証しない
  - 例: bioproject / biosample / insdc.sra 以外の `db_xrefs`、論文の雑誌名や DOI、2 人目以降の登録者の所属
- `hold_date` は、v1 では MSS の DATE 行の `YYYYMMDD`、v2 では ISO 8601 の `YYYY-MM-DD` で持つ。変換で書き方を直す
- v2 -> v1 で `trad_submission_category` が無いか `"WGS"` / `"GNM"` 以外なら `"GNM"` に、`division` が無ければ `"BCT"` にし、`UserWarning` を出す

## v2 から v3 への変換

`ddbj_record/converter/v2_to_v3.py` で変換する。v3 から v2 への converter は作らない。v3 の方が持てる情報が多く、戻すと失うため。v1 の record は v1 -> v2 -> v3 とつなぐ。

- v2 の項目は、ほぼ全て v3 に置き場がある。置き場が無く失うものは `UserWarning` を出し、変換は止めない
  - `submission.datatype`。v3 では `provenance.submission_category` から決めるので、`trad_submission_category` と同じ値なら黙って落とし、違う値のときだけ warning を出す
  - 論文の `consortiums` の名前以外。v3 の `Publication.consortiums` は名前の list
  - ST_COMMENT を表す experiment (`id` が `"st_comment_experiment"`) の `title` / `design` / `platform.instrument_model`
  - 論文の `year` と `date_published` が食い違うときの `year`。v3 の `date` は 1 つで、`date_published` を使う
- v2 に 1 つしか無い `submission.references` と `locus_tag_prefix` は、accession を持たない 1 つの project (`projects[0]`) に置く。`db_xrefs` は `relations` の `xref` に、ST_COMMENT の experiment は `sequences.structured_comments` に、`division` は全ての entry に置く
- v2 の qualifier の value `"true"` は、値の無い qualifier (`/pseudo` など) を表す。v3 では value を省く
- v3 は全てのフィールドが optional なので、v2 の空の list や dict は省く
